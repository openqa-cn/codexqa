# Case-generation subagent duty

> Shared by generate Phase 3 Step Two and update-skill `subagent-gen`.
> The main agent quotes this file **verbatim** into the subagent prompt and fills only path variables plus the pending-entry list. Do not summarise, re-step, add section titles, or rewrite constraint wording.
> After quoting, the subagent `read_file`s the listed artifacts itself.

**Subagent duty (run for all pending cases of the owned module)**:

> ⛔ **The subagent must do three things (missing any one is failure)**: ① generate all pending case files (.md) for this module → ② full in-module self-check (linter first, then the semantic pass in items 7a/7b; do not skip) → ③ report to the main agent (per entry including self-check result: pass / fail details)
>
> ⛔ **Must-read before writing files (easy to miss in template comments)**: the "Test data" table must keep `| Entity | Content | Construction |`; entity identifiers keep standard placeholders; construction/mutex conditions are written as text in the Content column and Construction is left empty; inside `<details>` write only request JSON, never expected response; do not append parameters in step descriptions (e.g. `deliveryType=4`); request params go in the engineering-info summary fold

1. Receive from the main agent: owned module name, the full pending `caseId` list for that module, plus each case's `caseName`, `filePath`, `caseType`, `category`, `source_design_ref`, `coverage`, and paths to `analysis.md`, `design.md`, `api-details.md`, `manual-case-template.md`, `case-authoring-rules.md`; **immediately after start, `read_file`**: full text of `analysis.md`, `design.md`, `api-details.md`, `manual-case-template.md`; `case-authoring-rules.md` only §1.4 case-generation constraints (content inclusion criteria, template structure requirements, request-param source priority); when `category=regression`, preconditions, steps, params, and assertions may use only the existing regression row pointed to by `source_design_ref`, and must not borrow incremental logic from the PRD, technical design, or analysis.md; do not rely on the main agent's paraphrase
2. Using verification points in `coverage` as the content basis, format the case `.md` file strictly per the `manual-case-template.md` template structure; do not write placeholder-judgment-criteria explanatory text into the case document; **step wording differs by caseType**: `SERVER` cases must write "→ trigger call `{fullClassName}.{methodName}` (read from the matching interface `<details>` block in `api-details.md`), request see X, engineering-info summary" — do not omit, and do not use semantic method-name abbreviations; `UI` case steps write only user-perspective operations (enter a page, click a button, type content, etc.); ⛔ do not appear "→ trigger call" or an interface name; expected results still assert API response/DB/cache, etc.; `**API response**` must state the interface name (e.g. `` `addCartItem` returns `code`=0 ``), not only `code`=0
3. **Fill rules for 1. Prerequisites / 4. Engineering Info submodules**: strictly align `manual-case-template.md` and `profile.components` in `integrations-resolved.json` — **1. Prerequisites** contains only client environment / data entities / Config service / Experiment / Mock / tracking info (Experiment only when the profile has `experiment` and this case involves it); **4. Engineering Info** contains only Server APIs + one section each for the profile's database / cache / mq. ⛔ Never write Server APIs/DB/Cache/MQ into Prerequisites, and never write Config service/Experiment/Mock into Engineering Info (the two places must not repeat content). All identifier field values must come from `analysis.md §1.3` original text; when not explicit, fill `TBD`; ⛔ do not infer:

   **3.a 1. Prerequisites submodule**:

   - **Config info (Config service)**: required when `coverage` has degradation/circuit-break/gray/experiment-group verification points, or the case needs to change a config switch to trigger; Config service serviceId/key/value are read from the `analysis.md §1.3` Config service row; fill `TBD` when unfilled
   - **Experiment**: required when `coverage` has gray/experiment-group verification points; experiment key is read from the `analysis.md §1.3 Experiment row; fill `TBD` when unfilled
   - **Mock**: required when `coverage` has downstream-exception verification points (timeout/error/unreachable, etc.); Mock service name (serviceId) and interface info are read from the `api-details.md` "## New downstream services" chapter; fill `TBD` when unfilled; Mock results are mutation-constructed from the full JSON in the matching downstream normal-response `<details>` block in `api-details.md` (e.g. change code to non-0, empty data, delayed return); do not write references such as "use baseline template" or "see Mock analysis"

   **3.b 4. Engineering Info submodule**:

   - **Server APIs**: required for cases that involve Server APIs calls; read serviceId, interface type (from `profile.protocols`), and interface name from the `analysis.md §1.3` Server APIs table + `api-details.md`, and fill one row per service in call order
   - **Database**: required when the expected segment of `coverage` involves DB assertion (write-path persistence, related-table consistency, update-scope convergence, read-path field mapping, etc.); shardingRule (sharded) or datasource (non-sharded) + table name are read from the `analysis.md §1.3` DB row; fill `TBD` when unfilled
   - **Cache**: required when the expected segment of `coverage` involves cache assertion; write only one "Cache" table whose columns are the profile `cache.fields`; values are read from the `analysis.md §1.3` Cache row; fill `TBD` when unfilled
   - **MQ**: required when the expected segment of `coverage` involves MQ assertion; write only one "MQ" table whose columns are the profile `mq.fields`; values are read from the `analysis.md §1.3` MQ row; fill `TBD` when unfilled

   - ⛔ **The "do not write if it does not affect execution" principle in case-authoring-rules.md §1.4 does not apply to the submodules above that have trigger conditions**: as long as `coverage` has the corresponding verification point, the corresponding submodule must be filled in the owning chapter above; do not delete it because it "does not affect execution"; ⛔ the Server APIs submodule is required whenever the case involves a backend call (not gated by coverage expected); delete the entire chapter for pure front-end UI cases that do not involve a backend call
4. **Data-source and placeholder rules**: the "1. Prerequisites > Test data" table keeps the `| Entity | Content | Construction |` structure from `manual-case-template.md`; each row must come from the same entity row in `design.md §2`; the data-entity name, content fields, and condition/mutex info must all be traceable to that row. Entity-identifier fields keep the corresponding `{placeholder}`; construction conditions, business constraints, and mutex conditions are written in natural language in the Content column; do not stuff conditions, business meaning, construction method, or meaningless serial numbers into placeholders; the Construction column must be empty. Interface request JSON in the engineering-info summary must come from the matching interface `<details>` request/response details in `api-details.md`; do not construct it yourself; **judge field by field**: depends on a data entity (identifier generated by the system) → keep the corresponding `{placeholder}`; determined directly by scenario semantics (e.g. `clientType`, `phone`, `deliveryType`, enums, operation type, engineering-location fields, custom numeric values, fixed flags) → write the real value; context carriers, Config service/Experiment/gray, Mock, environment variables, and cache switches are not test-data entities and go into request params, Prerequisites, or Engineering Info respectively. All entity-identifier placeholders are filled uniformly in the data-construction phase. **When the data-construction phase fills the Construction column, it must read the current `design.md §2` "dependencies" column and construct in topological order — depended-on entities before dependers; rules are in `case-authoring-rules.md` "Data construction order rules"**
5. ⛔ **Engineering identifiers + degradation rules**: follow the global "Engineering identifier rules"; concrete per-category degradation follows the DB/cache/MQ items under Step One "`expected` field assertion dimensions"
6. **File-output rules**: `.md` strictly uses the `filePath` field value; the file name is `caseName` (business-semantic), ⛔ do not name with `caseId` (UUID)
7. **Full in-module self-check (mandatory, cannot skip)**: after all pending `.md` files in this module are written, self-check **every** generated file in this module — not a sample, and not just the last one written. Run it in two passes, because they fail in different ways:

   **7a. Deterministic pass — run the linter, do not eyeball it.** Structural rules (table headers, empty Construction column, placeholder form, heading order, engineering-table fields) are mechanical, and a model reading them back tends to confirm what it just wrote. Run the script over the module directory instead:

   ```bash
   node --experimental-strip-types --experimental-default-type=module \
     "{skillRoot}/generation/quality-gates/lint_case_documents.ts" \
     --dir "usecases/cases/{module}" \
     --resolved usecases/testdocs/integrations-resolved.json
   ```

   `--resolved` matters: without it the engineering-table headers are compared against hard-coded defaults rather than this workspace's profile, so a valid case can be reported as broken. Fix every P0 it reports and re-run until clean. If the script is genuinely missing, fall back to checking the Step R4-3 deterministic rules by hand and say so in your report.

   **7b. Semantic pass — the part a script cannot do.** `read_file` `quality-gates/gate-case-quality.md` and apply its template-structure and semantic-quality checks: whether steps are executable, whether expected results assert concrete values instead of "success", whether the case actually covers its `coverage` entries. The linter has nothing to say about any of this.
8. **Report to the main agent**: report per entry `caseId`, `last_updated` (completion time), `business_rules_digest` (business-rule digest extracted from `.md` content), and self-check result (pass / fail finding details).
