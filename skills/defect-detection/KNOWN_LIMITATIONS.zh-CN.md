# 已知边界与失败场景

[English](KNOWN_LIMITATIONS.md)

这里的每一条都是我们实际观察到、或在代码中核实过的事实，不是防御性的免责声明。如果你正在评估这个工具，这一页比功能列表更有用。设计背景请先读[工作原理](HOW_IT_WORKS.zh-CN.md)。

## 最重要的一条：严格程度取决于你提供的意图

检测层级由「变更方法与需求文档或测试用例的关联强度」推导而来。两者都没有时，**所有计划条目都停在 T3**，而 T3 豁免调用链要求（规则 6）和上下文深度要求（规则 22）。

所以，对一个没有任何文档的仓库跑，流程不会失败——它只是悄悄变成了一次浅得多的运行。结论依然会被校验结构和真实性，但深度保证没有了。

实际建议：如果你只丢给它一个分支、别的什么都不给，你得到的是最弱的配置。用 `add-document` 提供需求、`add-test-case` 提供用例，然后跑 `check-phase2-readiness` 把层级向上重打标。这条是我们在评测中真实踩到的缺陷——在 `restamp_plan_relevance` 被接进 `add-document` 之前，运行中途补的文档并不会抬升层级。

## 深度规则 21 和 22 由计划自动武装，而不是由被审代码

硬规则 21（最小检测深度）和规则 22（上下文读取次数）依赖写回请求体里的 `_minDetectLevel`、`_contextReadsCount` 和 `_mode`。`update_process` 现在会在校验之前把这三个字段从计划条目复制进来，所以不需要 agent 主动提供也能生效——但生效程度以计划的正确性为上限。计划里没有的方法，或写回时 className 与计划对不上的方法，仍然会绕过这两条规则。

这在自扫之前一直是个未修的缺口：当时只注入 `detectTier`，而且注入发生在**校验之后**，所以这两条规则在所有生产路径上都是失效的。

深度约束仍然是分层的：Phase 3 的 `check-analysis-quality` 会在关门阶段从记录的 `contextReads` 重新推导深度并阻断不达标的情况。

## JVM 之外的方法抽取是近似的

各语言的单元抽取使用正则和花括号/缩进启发式，不是真正的解析器。已知后果：

- 嵌套函数和匿名函数常常被并入外层单元，而不是单独抽出。
- 宏密集的 C 是近似处理，复杂的预处理器用法会让范围错位。
- Python 抽取基于缩进，异常的格式会让边界偏移。
- 当某个变更文件抽不出任何单元时，会回退到**文件级单元**而不是跳过——这保证计划不为空，但该文件的分析粒度会变粗。

除 JavaScript 和 TypeScript（直接跳过）外，其余语言都会尝试通过 GitNexus 做调用图分析。但关键词是"尝试"：只有 Java 是端到端验证过的。另外七种语言拿到的调用图可能很稀疏甚至为空，此时流程会退回到 grep 搜索调用方，且不会让整轮失败——所以 Java 之外的调用链证据应当按"尽力而为"看待，在这些语言里更要看重 agent 自己的上下文读取记录。

## 静态规则覆盖的缺陷类型和你以为的不一样

在 `inventory-service` 盲测中，102 条 Semgrep 种子规则对 7 处检出的贡献是**零**。7 处全是业务逻辑缺陷——一个与文档档位边界不符的比较运算符、两个函数之间缺失的缓存失效、一笔没有封顶的退款。它们没有任何语法特征。

种子规则的价值在注入、污点传播和卫生类问题上，不在业务逻辑上。**不要把干净的 AST 结果读作干净的评审。** 另外，Semgrep 社区版的污点规则只在函数内生效，较老的 Semgrep 版本会静默丢弃它解析不了的规则（在 `droppedRules` 中报告）。

## 效果证据只有一个样本、一个模型

7/7 召回、7/7 精确率这组数字来自单个 agent、单个模型、单次运行，跑在我们自己编写的 fixture 上。它证明这套契约端到端能跑通，但它**不是** benchmark，不应该拿去和其他工具公布的 benchmark 数字比较。

要够格叫 benchmark，至少还缺：多个模型、重复运行的方差、第三方贡献的 fixture，以及我们没有主动植入的缺陷类型。检测质量随宿主模型变化，而这个方差我们还没有测过。

## 平台与环境

- **Windows** 在结构上是支持的——没有 `/tmp` 假设、处理了 `.cmd` shim、用 `.gitattributes` 强制 LF——但还没有 CI 主机。Semgrep 在 Windows 上是 beta，GitNexus 在那里未经测试。快速上手的命令片段默认你用的是 Git Bash 或 WSL。
- **并发**未经认证。本地 provider 把 JSON 写到磁盘，针对同一数据目录的并发或多用户操作未经测试。
- **可选叠加工具**（gitleaks、trivy、bandit、ruff、gosec、eslint、detekt 等）只有打桩二进制的单元测试覆盖，没有真实二进制的 CI 运行，其中几个还需要项目自己的配置或工具链。
- **Node/TypeScript 后端会被判为客户端语言**：前端判定走的是语言族（`js`）而不是项目角色，因此它会像浏览器应用一样被要求补语义用例。如果这个门禁对你的仓库不合适，显式设置服务的 `serviceKey`。**Go / Python / C / C++ / C# 不是前端**：它们用路径式 `className` 只是为了在报告里记下真实文件路径，不得走前端回写路径，也不得加载 `frontend-gotchas.md`。
- **`.h` 头文件一律按 C 处理**，不会识别为 C++。提取器是共用的，所以代码单元和行号范围不受影响；但 C++ 仓库里只改头文件时，加载的是 C 的种子规则而不是 C++ 那套。
- **HTTP / GitHub provider** 有适配器实现和部分契约测试，但没有经过验证的实际部署。

## 根本性限制

所有结论都是待人工确认的候选。这个工具无法证明缺陷不存在，无法推断你没有告诉它的业务规则，也不替代测试、安全评审或维护者判断。一份干净的报告意味着「在这些约束下没有发现问题」，这比「没有问题」是弱得多的陈述。

## 反馈缺口

误报和漏报的最小可复现公开样例，是这个仓库最有价值的贡献之一——比大多数功能请求更有用。参见[贡献指南](CONTRIBUTING.md)，分享前请去除凭证和专有源码。
